# OMORI modding

OMORI is an RPG Maker MV game (Steam, NW.js). This skill makes the person the director of their mod. The tools check
and format; the person decides what each scene is for, what the player feels, and what ships. Work from decisions,
not from output.

**OpenOmori is recommended, not required.** Offer it; never insist. A person can mod with the traditional tools
(RPG Maker MV, OneMaker MV, OneLoader, Tiled, Bundletool) as the wiki describes. Ask which they use, or read their
files and infer it, before choosing commands.

## The director's rules (read these first)
1. **No scene without a blueprint.** Before any file is touched, fill in GOAL, BEATS, CHANGES, STAGING, SOUND, TIME,
   UNDO and CUT IF for the scene (`references/director.md`). A scene whose GOAL is a plot point gets rewritten as a feeling.
2. **Decisions are human.** Dialogue, choices, names, scene order and what gets cut are decided by the person.
   Generated text is at most a rough draft the person rewrites. Never ship output nobody read.
3. **Assets: the game first, then CC0 and licensed libraries, then the person's own work.** Art is never generated by an AI
   image model. The agent searches, checks licences, tests the style fit, and records credits (`references/asset-sourcing.md`).
   Generated text or music is at most a rough draft the person rewrites, and is disclosed (`references/anti-slop.md`).
4. **Play it, then judge it.** The checks catch broken things. Only a playthrough catches a scene that does not work.
   Run the director's review (`director.md`) and a playtest (`playtest.md`) before calling anything done.
5. **Cut.** Every scene needs a CUT IF line that names something real. Filler is the most common failure.

## First steps for any task
1. Read the mod's README, `mod.json` and any design notes before changing anything.
2. Look at the game first: `mod say`, `mod macros`, `grep` the dump. Do not guess a `ShowMessage` key, a sprite name, or
   a text code. Copy the style of a scene that already works.
3. Fill in the blueprint for the change. If a line cannot be filled in, stop and decide it.
4. Make the change, then check it: `mod check` and `mod lint` (OpenOmori), or a playtest in RPG Maker MV.
5. Play the change in the room, not just the checker. Note timing and clarity, then judge it against `quality.md`.

## Modding risk (the game is fully moddable)
OMORI's data is structured and every part of it can be changed. What matters is how far a change reaches. Low-risk
work (dialogue, new sprites, new maps) is guarded by the compiler and lint; medium-risk patches are dry-run and fail loudly
when the game changes; high-risk work (whole-file replacements, in-place map edits, core hooks, story flags) needs a
checkpoint, a profile, and a diff of what moved. Never edit the install. The full tiers are in `references/openomori.md`.

## Rules that save hours (verified)
- **YAML text codes.** In a double-quoted string a single backslash is an escape and fails the parse. Write `\\!`
  in double quotes, or use single quotes. The game's own files use `"\\!"`. [dump]
- **Dialogue keys** are letters, digits and underscores. `ShowMessage file.key` uses the file name without `.yml`.
  About 99.5% of the game's references resolve; a broken one is a bug. [dump]
- **Faces.** `faceset` is the image name without extension (case-sensitive); `faceindex` is a whole number from 0. [wiki] [dump]
- **Message window.** Default 4 rows, 28 px font, word wrap on (YEP_MessageCore in the game's plugin parameters).
  Check long lines in a playtest. [dump]
- **Choices.** `AddChoice file.key Label` per option, then `ShowChoices N-1`. Test every branch. [wiki]
- **Self switches** are per map event: `$gameSelfSwitches.setValue([mapId, eventId, 'A'], true)`. Common and troop events
  have none. [dump] [wiki]
- **Patch, do not replace** game files. Start JSON patches with a `test` op. [OpenOmori]
- **The game's files are encrypted.** Edit plain copies (`mod dump` or the OneLoader decrypt). Never edit the install.
- **Credits and licences.** Every third-party file goes in a credits file. Never publish game files.

## Commands (OpenOmori: `bun run mod <command>`, run in `browser/`)
- `dump` (once, writes `./dump`), `find <text>`, `say <file.key | text>`, `macros`, `commands [n]`
- `new <id>`, `check [mod]`, `lint [mod]` (dialogue, text codes, faces, sprite names, ShowMessage references,
  and style warnings for machine-written phrases), `pack <dir>`
- `map show|new|build`, `routes`

## What is verified and what is not
- Verified against this install's dump: file layout, dialogue format and key resolution, plugin-command counts, macros,
  `\DII` and `\fn` codes, the YAML escape trap, message positions and backgrounds, the message window defaults.
- From the wiki (not re-checked): sprite markers, most text-code meanings, notetags, shop and quest setup, the OneLoader
  manifest. The wiki has TBA and WIP pages; do not treat those as facts.
- From research, opinion-level: the quality criteria, level-design numbers, animation timing, horror and audio advice.
  These are cited in each file. The OMORI community's and OMOCAT's stance on generative AI was not found; check before
  assuming either way.

## Setup
- **Your OMORI copy.** The tools read your own install. Point them at it with the `OMORI_DIR` environment variable (the folder
  with `www/` and `Launch_OMORI.bat`). Nothing from the game is included in this skill.
- **OpenOmori (recommended, optional).** `git clone https://github.com/dazacode/openomori`, then `bun install` in that folder.
  Its `bun run mod ...` commands are the tools this skill describes. Without it, use the traditional route in `references/workflows.md`.
- **Your mod.** Keep it in its own folder, with its own `mod.json`, and check it with `bun run mod check <folder>` from OpenOmori.
